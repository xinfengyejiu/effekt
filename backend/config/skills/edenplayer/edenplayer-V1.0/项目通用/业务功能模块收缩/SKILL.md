# PRD 编号模块层级

## 目标

在根据 PRD、需求文档、用户故事、功能说明、接口说明、UI 交互说明或业务规则生成测试用例时，`module_name` 必须严格跟随 PRD 的编号或标题层级，并结合实际内容分析补齐三级、四级模块。仅对可测试的业务功能、后台操作、用户流程、验收标准、非功能要求或明确业务规则生成模块；`文档说明`、`文档目的`、`资料来源`、`产品定位`、`用户角色说明`、`版本规划`、`待完善事项清单`、`风险与注意事项`、`附录` 等元信息或背景章节只作为理解上下文，不生成测试用例模块，除非其中包含明确可执行、可验证的业务行为。PRD 有几个可测试一级大点，就生成几个一级模块；每个大点下的可测试小点继续作为二级模块；如果 PRD 没有显式三级或四级编号，则根据子标题、表格功能项、业务规则、验收项和流程节点继续细分到三级、四级。模块名称尽量直接使用各编号标题、表格功能名或实际分析出的功能点名称，不主动把数字编号前缀写进模块名。

本技能不改变测试用例覆盖目标，只约束模块组织方式和平台入库 JSON 输出格式。

## 适用场景

使用本技能处理以下任务：

- 根据 PRD 或需求说明生成测试用例
- 根据用户故事、功能清单、页面说明生成测试用例
- 根据接口说明、业务规则、状态流转补充测试用例
- 优化、评审、改写已有测试用例，尤其是需要调整 `module_name` 的场景
- 用户明确提到“模块太散”“一级模块太多”“功能模块收缩”“大模块套小模块”“按业务域归类”等诉求

## 核心原则

### 1. 一级模块严格等于 PRD 一级编号

生成用例前，先识别 PRD 的一级编号或一级标题，并排除只提供文档背景、资料来源、附录说明、版本计划或风险提示的非测试章节。一级模块数量必须与 PRD 中可测试的一级编号数量一致。

- PRD 有 5 个一级大点，则一级模块就是这 5 个点。
- 不要把页面、按钮、入口、组件、状态、异常提示或单个操作额外提升为一级模块。
- 不要自行合并或拆分 PRD 一级编号，除非 PRD 明确说明这些内容属于同一范围。

### 2. 子编号继续映射为下级模块

`module_name` 使用“一级模块/二级模块/三级模块/四级模块”格式。PRD 的子编号继续映射为下级模块。

- 一级编号下有 7 个小点，则该一级模块下生成 7 个二级模块。
- 小点继续包含编号或标题时，继续映射到三级、四级模块。
- 最多保留四级模块；超过四级的更深细节写入 `title`。

示例：

- 合适：`账号登录与访问权限/登录认证/验证码登录/验证码过期校验`
- 合适：`社区内容/帖子详情/评论互动/发表评论`
- 不合适：PRD 只有 5 个一级编号，却生成 12 个一级模块。

### 3. 没有编号时智能推断编号层级

如果 PRD 没有明确编号，需要先智能推断一套隐含编号层级，再按该层级映射模块。

- 根据标题大小、目录结构、列表缩进、表格分区、功能组、用户流程和语义段落推断一级到四级层级。
- 顶层标题、目录主项、大型功能区或重复出现的主要主题块作为一级模块。
- 子标题、缩进列表、表格小节、功能组和从属流程作为二级、三级、四级模块。
- 没有下级标题但存在大量场景时，保持在最近的推断模块下，用 `title` 表达具体场景。

### 4. 不为未知需求编造模块

如果需求信息不足，仍然输出测试用例，但在相关字段中标记“待确认”。不要为了让模块看起来完整而编造不存在的 PRD 编号或业务能力。

可使用：

- `待确认/待确认/待确认/待确认`
- `账号与权限/待确认/待确认/待确认`
- `内容管理/待确认/待确认/待确认`

根据已知 PRD 编号或标题选择最接近的父模块；完全无法判断时再使用“待确认”。

## 模块分级方法

生成测试用例前，按以下顺序处理模块：

1. 先识别 PRD 的显式编号或标题层级，一级模块严格跟随 PRD 一级编号或顶层标题，二级模块跟随其下级编号或标题。
2. 如果 PRD 只有一级、二级编号，三级和四级需要按照实际分析结果补齐：优先使用 `####` 等子标题、需求表格中的模块/功能行、业务规则分组、验收项、用户流程节点和语义上从属于当前模块的功能点。
3. 不要把页面、按钮、入口、组件、状态、异常提示或单个操作提升为一级模块；这些内容只有在确实属于某个父模块下的功能细分时，才可作为三级或四级模块。
4. 同一父模块下的三级、四级模块应来自真实需求内容，不能为了凑满层级而编造不存在的业务能力。
5. 为每条测试用例填写 `module_name`，使用同一套模块命名，避免同义词混用；模块名称尽量使用 PRD 标题、表格功能名或实际分析出的功能点名称。

## 推荐模块命名风格

模块名应短、稳定、业务化。优先使用名词或名词短语。

推荐：

- `账号与权限/登录认证/账号密码登录`
- `搜索与发现/搜索结果/多语言检索`
- `社区内容/首页发现/内容推荐`
- `社区内容/帖子详情/评论互动`
- `用户关系/收藏关注/关注作者`
- `通知中心/消息通知/系统公告`
- `个人中心/账号设置/资料编辑`
- `媒体内容/视频播放/Playlist 播放`
- `内容治理/举报拉黑/帖子举报`
- `运营后台/配置管理/榜单配置`
- `全局规则/异常状态/网络异常`

避免：

- 把“登录”“注册”“忘记密码”“验证码”“权限不足”全部作为一级模块
- 把“点赞”“评论”“转发”“分享”“收藏”全部作为一级模块
- 把页面名称、弹窗名称、按钮名称直接作为一级模块
- 同一业务反复使用不同叫法，例如“个人设置”“用户设置”“账号设置”混用

## 测试用例生成要求

### 覆盖范围

在需求范围内，优先覆盖：

- 正常主流程
- 关键业务规则
- 权限与角色差异
- 输入校验与边界值
- 状态变化与数据一致性
- 异常态、空态、加载态、失败重试
- 多语言、国际化、兼容性等明确提到的非功能要求
- 后台配置对前台展示或业务行为的影响

如果需求没有提供某类规则，不要编造。可在相关字段标记“待确认”。

### 用例标题

`title` 必须细化到具体场景，能让测试人员直接理解要验证什么。

推荐：

- `账号密码正确时登录成功并进入社区首页`
- `未登录用户点赞帖子时提示登录`
- `切换英文语言后搜索结果页文案同步更新`

避免：

- `登录测试`
- `帖子详情测试`
- `异常测试`

### 前置条件

`precondition` 写明执行用例前必须满足的账号、数据、配置、环境或状态。信息不足时写“待确认”。

### 步骤与预期

`steps` 和 `expected_result` 每一行都必须带数字编号，并保持对应关系。

格式示例：

`steps`: `1. 打开登录页\n2. 输入已注册账号和正确密码\n3. 点击登录按钮`

`expected_result`: `1. 登录页正常展示\n2. 输入内容被正确接收\n3. 登录成功并跳转到目标页面`

## 输出格式

最终只输出一个 JSON 对象，不输出 Markdown、解释文本、代码块或额外说明。

JSON 对象必须符合以下结构：

{
  "cases": [
    {
      "title": "用例名称/测试点名称",
      "module_name": "一级模块/二级模块/三级模块/四级模块",
      "precondition": "前置条件",
      "steps": "1. 步骤一\n2. 步骤二",
      "expected_result": "1. 预期结果一\n2. 预期结果二",
      "priority": 2,
      "case_type": 1,
      "tags": ["AI生成"]
    }
  ]
}

字段要求：

- `cases`：测试用例数组。
- `title`：细化到具体测试场景。
- `module_name`：使用“一级模块/二级模块/三级模块/四级模块”，并严格遵循 PRD 编号或标题层级；一级、二级优先按 PRD 显式编号或标题，三级、四级在无显式编号时按实际分析结果从子标题、表格功能项、业务规则、验收项和流程节点中提取，最多四级。
- `precondition`：无明确前置条件时可写“无”；信息不足时写“待确认”。
- `steps`：字符串，每行以数字编号开头。
- `expected_result`：字符串，每行以数字编号开头，与步骤对应。
- `priority`：默认使用 `2`，除非用户或平台规则明确指定其他优先级。
- `case_type`：默认使用 `1`，除非用户或平台规则明确指定其他类型。
- `tags`：默认包含 `["AI生成"]`；如用户提供标签，可在保留“AI生成”的基础上追加。

## 处理信息不足

当需求描述缺少关键规则时：

- 不要补写不存在的产品逻辑。
- 在 `precondition`、`steps`、`expected_result` 或 `module_name` 中使用“待确认”。
- 仍然围绕已知需求生成可执行或可评审的测试点。

示例：

- 登录失败次数上限未说明：预期结果写“连续失败后的锁定规则待确认”。
- 榜单排序规则未说明：步骤可验证入口与展示，排序预期写“榜单排序规则待确认”。
- 多语言支持范围未说明：模块可写 `搜索与发现/多语言/待确认`。

## 质量检查

输出前检查：

1. 是否只输出 JSON 对象。
2. `cases` 是否为数组。
3. 每条用例是否包含所有必填字段。
4. `module_name` 是否体现 PRD 编号或标题层级，最多四级。
5. 一级模块数量是否严格等于 PRD 一级编号或顶层标题数量。
6. 同类功能是否使用一致的模块命名。
7. `title` 是否是具体场景，而不是泛泛模块名。
8. `steps` 和 `expected_result` 是否每行都有数字编号。
9. 信息不足处是否标记“待确认”，没有编造需求。
10. `tags` 是否至少包含“AI生成”。
