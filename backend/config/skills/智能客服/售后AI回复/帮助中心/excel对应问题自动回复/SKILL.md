# Excel对应问题自动回复测试用例生成

## 目标

根据用户提供的 PRD、需求说明、Excel 表结构、问答映射规则或样例数据，生成用于验证“根据 Excel 中的问题匹配对应 answer 并自动回复”的测试用例。

该 Skill 重点帮助测试平台覆盖以下能力：

- Excel 中每个问题是否能匹配到正确 answer。
- 自动回复内容是否严格来自对应问题映射的 answer。
- 多问题、多轮提问、相似问题、异常数据、缺失数据等场景下是否按需求处理。
- 测试用例的 expected_result 中必须体现对应问题映射的 answer 检查。

## 固定触发场景

当用户基于以下任一内容生成、补充、优化或评审测试用例时，应按本 Skill 执行：

- PRD 或需求文档
- Excel 问答表、问题库、FAQ 表、知识库表
- 用户故事或功能说明
- 接口说明
- UI 交互说明
- 业务规则
- 自动回复、客服机器人、问答匹配、answer 映射相关需求

## 输出格式要求

最终只输出 JSON 对象，不输出 Markdown、解释文本或代码块。

输出结构必须为：

{
  "cases": [
    {
      "title": "用例名称/测试点名称",
      "module_name": "一级模块/二级模块/三级模块/四级模块",
      "precondition": "前置条件",
      "steps": "步骤1\n步骤2",
      "expected_result": "预期结果1\n预期结果2",
      "priority": 2,
      "case_type": 1,
      "tags": ["AI生成"]
    }
  ]
}

字段要求：

- title：细化到具体场景，避免只写“自动回复测试”。
- module_name：优先按 PRD 编号或标题层级填写，最多四级；一级、二级优先按 PRD 显式编号或标题，三级、四级在无显式编号时按实际分析结果从子标题、表格功能项、业务规则、验收项、流程节点和语义上从属的功能点中提取；编号只用于判断层级，模块名称尽量直接使用各编号标题、表格功能名或实际分析出的功能点名称；如果 PRD 没有编号，需要根据标题、目录、列表缩进、表格分区、功能组和语义段落智能推断隐含编号层级；信息不足时使用合理的“自动回复/Excel问答映射/具体子功能/具体场景”层级。
- precondition：描述 Excel 数据、系统配置、登录状态、导入状态等前置条件；信息不足时写“待确认”。
- steps：每一行必须带数字编号，例如“1. 导入包含问题和answer字段的Excel”。
- expected_result：每一行必须带数字编号，且必须包含对对应问题映射 answer 的检查。
- priority：默认 2；高风险核心链路可设为 1，低频或兼容性场景可设为 3。
- case_type：默认 1。
- tags：至少包含“AI生成”，可额外加入“Excel”“自动回复”“问答映射”等标签。
- 信息不足时标记“待确认”，不能编造需求。

## 测试用例设计思路

生成用例时按以下步骤推理：

1. 识别 Excel 中的关键字段  
   优先识别问题字段和答案字段，例如：question、问题、提问、用户问题、answer、答案、回复内容、标准回复。  
   如果字段名不明确，在用例中标记“待确认”。

2. 建立问题与 answer 的映射关系  
   对每条有效数据，理解为“输入该问题后，系统应自动回复该行对应 answer”。  
   expected_result 必须明确校验：回复内容等于或包含该问题映射的 answer，具体取决于需求描述。

3. 区分匹配规则  
   如果需求说明了精确匹配、模糊匹配、关键词匹配、相似度匹配、大小写不敏感、去除空格等规则，应分别生成对应场景。  
   如果匹配规则未说明，应生成“匹配规则待确认”的测试用例，不要自行假设。

4. 覆盖正常、异常和边界场景  
   既要覆盖正常问题命中 answer，也要覆盖无匹配、重复问题、空问题、空 answer、特殊字符、超长文本、多语言、换行、前后空格等情况。

5. 检查自动回复结果  
   每条用例的 expected_result 应关注：
   - 是否命中正确问题。
   - 是否返回该问题对应 answer。
   - 是否没有串答、错答、漏答。
   - 未命中时是否按需求返回默认回复或提示；未提供默认规则时标记“待确认”。

## 必须覆盖的核心场景

在需求信息足够时，优先生成以下测试用例：

### 1. 单条问题精确命中

验证用户输入与 Excel 中某个问题完全一致时，系统自动回复该行 answer。

expected_result 中应包含类似检查：

- “系统返回该问题在 Excel 中映射的 answer：xxx”。
- 如果没有具体 answer 样例，则写“系统返回该问题对应的answer，具体内容待确认”。

### 2. 多条问题分别命中

验证 Excel 中存在多条问题-answer 映射时，不同问题分别返回各自 answer，不能串答。

### 3. 相似问题或近似表达

如果需求支持模糊匹配，验证相似问法能匹配到正确 answer。  
如果需求未说明模糊匹配，生成待确认用例，提示需确认相似问题是否应命中。

### 4. 未匹配问题

验证用户输入的问题在 Excel 中不存在时，系统按需求返回默认提示、转人工、无结果提示或其他指定处理。  
如果未提供规则，expected_result 标记“未匹配问题处理方式待确认”。

### 5. answer 为空或缺失

验证问题存在但 answer 为空时，系统如何处理。  
不要编造默认回复，应标记或检查需求中的指定行为。

### 6. 问题为空或无效

验证 Excel 中问题字段为空、空格、特殊字符或无效数据时，系统导入、解析和匹配行为是否符合需求。

### 7. 重复问题对应不同 answer

验证 Excel 中出现重复问题且 answer 不一致时，系统如何处理，例如导入失败、提示重复、取第一条、取最新一条等。  
如果需求未说明，标记“重复问题处理规则待确认”。

### 8. answer 内容格式保持

如果 answer 包含换行、链接、数字、标点、富文本、特殊符号，应验证自动回复是否保持原内容或按需求格式化。

### 9. Excel 导入与更新后生效

如果需求涉及上传或更新 Excel，应验证导入成功后新映射生效、更新 answer 后回复同步变化、删除问题后不再命中。

### 10. 权限与配置

如果需求涉及后台配置、知识库选择、租户、角色权限，应覆盖有权限和无权限用户对 Excel 问答映射的导入、查看、使用场景。

## expected_result 编写规则

expected_result 是本 Skill 的重点。每条用例必须体现“对应问题映射的 answer 检查”。

优先使用以下表达：

- “系统自动回复内容应与 Excel 中该问题对应的 answer 一致”。
- “系统返回问题【X】映射的 answer【Y】”。
- “系统不应返回其他问题对应的 answer”。
- “当未命中任何问题时，系统按需求返回默认回复；默认回复内容待确认”。

如果用户提供了具体 Excel 样例，例如：

- 问题：如何退款？
- answer：进入订单详情页点击申请退款

则 expected_result 必须写明：

1. 系统识别用户问题“如何退款？”命中 Excel 中对应记录
2. 系统自动回复“进入订单详情页点击申请退款”
3. 系统未返回其他问题的answer

如果用户没有提供具体 answer，不要编造答案，应写：

1. 系统识别用户问题命中 Excel 对应记录
2. 系统自动回复该问题映射的answer，具体answer内容待确认

## 用例粒度要求

- 每条用例只验证一个清晰场景。
- title 应体现具体问题、匹配方式或异常类型。
- 不要把所有问题映射塞进一条大用例，除非用户明确要求批量验证。
- 对 Excel 中多条代表性数据，可生成多条用例分别验证。
- 对同类数据很多的情况，选择代表性样例，并补充批量校验场景。

## 信息不足处理

当输入需求缺少以下信息时，不要编造：

- Excel 字段名
- 具体 question 和 answer
- 匹配规则
- 未命中默认回复
- 重复问题处理规则
- answer 为空时的处理方式
- 导入失败提示
- 权限规则
- 生效时机

应在 precondition、steps 或 expected_result 中写“待确认”。

示例：

- “Excel中问题字段和answer字段名称待确认”。
- “系统按未匹配问题处理规则返回提示，具体提示内容待确认”。
- “重复问题对应不同answer时的优先级规则待确认”。

## 推荐模块命名

根据需求内容选择合适模块名：

- “自动回复/Excel问答映射/问题命中回复”
- “自动回复/Excel问答映射/未命中处理”
- “自动回复/Excel问答映射/异常数据处理”
- “自动回复/Excel问答映射/Excel导入更新”
- “自动回复/Excel问答映射/权限配置”

## 优先级建议

- priority = 1：核心链路，例如有效问题命中正确 answer、错误串答风险、线上高频场景。
- priority = 2：一般功能场景，例如未命中、更新生效、格式保持。
- priority = 3：低频兼容场景，例如特殊字符、多语言、极长文本等。

## 生成前检查清单

输出前自检：

1. 是否只输出 JSON 对象。
2. JSON 是否包含 cases 数组。
3. 每条用例是否包含 title、module_name、precondition、steps、expected_result、priority、case_type、tags。
4. steps 和 expected_result 是否每行都有数字编号。
5. 每条 expected_result 是否包含对应问题映射 answer 的检查。
6. 是否避免编造未提供的 answer 或规则。
7. 信息不足处是否标记“待确认”。
8. tags 是否至少包含“AI生成”。
